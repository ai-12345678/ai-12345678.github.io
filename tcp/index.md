# TCP 的 ACK 标志位与 Seq/Ack 序号说明

## 1. ACK 标志位

握手完成后，正常通信报文通常设置 `ACK=1`，表示报文中的 **Ack 确认号有效**。

ACK 标志位与 Ack 确认号是两个字段。带 ACK 标志的报文可以同时携带数据，也可以同时带有 SYN 或 FIN。

## 2. 同一方后续发送的 Seq

发送**纯 ACK，没有数据，也没有 SYN/FIN**时，不消耗发送序号，因此**同一方紧接着发送新数据时，Seq 保持不变**：

```text
A 发送纯 ACK：Seq=1001，数据长度=0
A 随后发数据：Seq=1001
```

这里说明的是 A 自己的 Seq 不变。纯 ACK 通常不会触发对方再回复 ACK。

## 3. Seq 和 Ack 的含义及握手、挥手示例

**Seq 是本报文的发送序列号；Ack 是对对方内容的确认号，表示下一次期望收到的对方序号。**

按序连续收到普通新数据时，通常有：

```text
回复报文的 Ack = 收到报文的 Seq + 数据字节数
```

若收到的报文包含 **SYN 或 FIN，还需额外加 1**。如果存在乱序或数据缺失，Ack 按实际累计接收进度计算。这里的数据长度仅指 TCP 携带的数据，不包含报文头。

| 报文内容 | 占用的序号数量 |
| --- | ---: |
| 纯 ACK，无数据 | 0 |
| SYN 或 SYN+ACK，无数据 | 1 |
| FIN 或 FIN+ACK，无数据 | 1 |
| 普通数据，N 字节 | N |
| SYN+ACK 或 FIN+ACK，同时携带 N 字节数据 | N+1 |

**ACK 标志本身不占序号，但不会抵消 SYN、FIN 占用的序号。Seq 和 Ack 分别跟踪两个方向，不能仅根据收到的 Ack 决定本方报文的 Seq。**

### 3.1 三次握手：不携带应用数据的示例

假设 A 主动连接 B，A 的初始序号为 `1000`，B 的初始序号为 `5000`。

| 步骤 | 方向 | 标志位 | Seq | Ack | 数据长度 |
| --- | --- | --- | ---: | ---: | ---: |
| 第一次握手 | A → B | SYN | 1000 | — | 0 |
| 第二次握手 | B → A | SYN、ACK | 5000 | 1001 | 0 |
| 第三次握手 | A → B | ACK | 1001 | 5001 | 0 |

- 第一次握手未设置 ACK 标志，Ack 字段无效，用“—”表示。
- 第二次握手的 `Ack=1001`：确认 A 的 SYN，计算为 `1000 + 0 + 1`。
- 第三次握手的 `Seq=1001`：A 自己的 SYN 已占用序号 1000；`Ack=5001` 则确认 B 的 SYN，计算为 `5000 + 0 + 1`。
- 第三次握手是纯 ACK，不再消耗发送序号。因此随后 A 的新数据从 `1001` 开始，B 的新数据从 `5001` 开始。

握手报文也可以携带数据：第三次握手的 ACK 可以携带应用数据；前两次的 SYN、SYN+ACK 通常不带应用数据，但协议也允许携带。携带的数据需要计入对应方向的序号。

### 3.2 四次挥手：期间不传输应用数据的示例

接着上面的握手，假设双方尚未传输应用数据，由 A 主动关闭连接。

| 步骤 | 方向 | 标志位 | Seq | Ack | 数据长度 |
| --- | --- | --- | ---: | ---: | ---: |
| 第一次挥手 | A → B | FIN、ACK | 1001 | 5001 | 0 |
| 第二次挥手 | B → A | ACK | 5001 | 1002 | 0 |
| 第三次挥手 | B → A | FIN、ACK | 5001 | 1002 | 0 |
| 第四次挥手 | A → B | ACK | 1002 | 5002 | 0 |

- A 的 FIN 占用序号 `1001`，所以 B 确认时使用 `Ack=1002`。
- B 第二次挥手发送的是纯 ACK，不消耗序号，因此第三次挥手的 `Seq` 仍是 `5001`。
- B 的 FIN 占用序号 `5001`，所以 A 最后确认时使用 `Ack=5002`。
- A 最后的 `Seq=1002`，是因为 A 自己的 FIN 已占用序号 1001；这个纯 ACK 不再消耗序号。

客户端、服务端都可以主动关闭连接。四次挥手是常见的分步过程；如果中间的 ACK 与 FIN 合并发送，报文数量可以减少。

### 3.3 挥手期间继续发送剩余数据的变化

收到对方 FIN 后，本方仍可继续发送剩余数据，直到本方也发送 FIN。

例如，如果 B 在上述第二次挥手之后，从 `Seq=5001` 开始又发送了 **100 字节**：

- 数据占用序号 `5001～5100`。
- B 随后的 FIN+ACK 使用 `Seq=5101，Ack=1002`。
- A 最后的纯 ACK 使用 **`Seq=1002，Ack=5102`**。

A 的 Seq 仍是 1002，因为 A 没有再发送新数据；Ack 增加到 5102，因为 A 已按序收到 B 的 100 字节数据和 FIN。

FIN 也可以与最后一段数据放在同一个报文中。对方按序收到该报文后，确认号为 `Seq + 数据长度 + 1`。单纯等待或收到 ACK，不会额外消耗本方发送序号。
